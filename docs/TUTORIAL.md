# 从本仓库成为 Agent 应用工程师

面向：已有 Python / 后端 / 服务器 / 数据库基础，希望把「能跑的 Agent demo」做成「接近真实上线形态」的人。

本仓库当前代码 = **v0.2**。v0.1 是历史形态（单文件），不必还原，但必须理解「为什么拆」。

天气查询只是载体。每一版练的是真实 Agent 产品里都会出现的工程能力，而不是天气业务本身。

---

## 0. 怎么用这份文档

### 给你自己

1. 先用 **2 周、每个工作日 1 小时** 读懂术语 + 角色 + v0.2（见第 2 节）。
2. 再用 **约 13 周、每个工作日 3 小时** 按 v0.3 → v1.0 推进（见第 3 节）。
3. 每一版只攻克一个能力。做完对照「验收」，再进入下一版。
4. 术语看 `docs/GLOSSARY.md`。正文只点名，不重复解释。

### 给后续帮你改代码的 AI（强制约束）

你正在改进 `agent-learning` 仓库。必须遵守本文 **当前目标版本**，禁止跨版本把后面的功能提前做完。

架构边界（v0.2 已确立，后续不得破坏）：

1. Agent **不直接操作** `messages` 列表；只通过 Session / Memory API。
2. 新 Tool：独立模块 + `schema` + `execute` + 注册到 Registry。禁止在 `main.py` 里写死工具列表与 if/else。
3. System Prompt 只放 `agent/prompt/*.txt`，禁止写回 Python 字符串。
4. 日志按 USER / LLM / Tool 分段；不要用 print 代替 Logger。
5. 不要靠「再加几个无关 Tool」制造进度。每一版的目标写在「本版只解决什么」。
6. 改完必须对照该版本「验收标准」。未写进该版本的能力（RAG、流式、画像等）一律不做。
7. 少贴业务代码到文档；实现细节以仓库代码为准。本文只定义 **目标、边界、验收、任务**。

请求 AI 时的模板：

> 请只实现 `docs/TUTORIAL.md` 中的 **v0.x**。不要做后续版本的功能。
> 保持 Session / Memory / Registry / Prompt / Logger 边界。
> 对照该节「验收标准」自检。

## 1. 你要成为的角色

**Agent 应用工程师**：把大模型嵌进软件系统，让它稳定地完成任务。

你要会的不是训练模型，而是：

| 会做 | 不会（至少现阶段不必） |
|------|------------------------|
| 设计 Agent 循环、Tool 契约、Session/Memory | 从零训练 LLM |
| 控制送进模型的上下文 | 推导 Transformer 公式 |
| 把 Agent 做成 HTTP 服务、可观测、可评测 | 研究新模型结构 |
| 处理失败、确认、权限、费用 | 把框架当黑盒堆起来 |

本仓库的路线是：**先手写核心，再按需引入框架**。这样以后用 LangGraph / MCP / 各家 Agent SDK 时，你知道它们在替你做什么。

## v0.1 单文件能跑（历史，0 天实现）

**真实业务里的问题：** 先证明「模型 + 工具」能闭环。所有产品都从这里开始。

**本版只解决什么：** 终端里能聊；问天气会调工具；不问天气就直接答。

**形态：** 一个 `.py`。`messages` 是全局列表，`TOOLS` 写死，prompt 写死，没有 Session，没有持久化。

**要懂的术语：** LLM、Prompt、messages、role、Tool、Function Calling、Agent 循环、幻觉。

**为何必须拆掉它（对应 v0.2）：** 第二个工具、第二种存储、第二个用户同时出现时，单文件会把「协议 / 存储 / 工具 / 提示词」缠死。

**验收（概念）：** 能说出单文件版的 4 个致命点：消息、工具、提示词、会话 都没有边界。

**给 AI：** 不要把项目改回单文件。v0.1 只存在于认知里。

---

## v0.2 模块化运行时（当前仓库 · 前两周读懂）

**真实业务里的问题：** 要能加第二个 Tool、换存储、换角色提示词、按人区分对话，并且出了问题能回放。

**本版已解决：**

- Session：一次对话一个 `session_id`
- Memory：Agent 只 `load` / `add_*`；内存版与 PostgreSQL 版同一套 API
- Tool：`schema` + `execute` + Registry
- Prompt：文件加载，可换名字
- Logger：USER / LLM / Tool 分段，写文件

**对照本仓库（精读顺序）：**

1. `agent.py` → 转到 `agent.main`
2. `agent/main.py` → `chat_once` 循环（项目心脏）
3. `agent/session.py` → 门面，本身不存消息
4. `agent/memory/history.py` 与 `postgres.py` → 存哪、怎么拼回 messages
5. `agent/tool/` → 协议、天气、注册表
6. `agent/llm/client.py` → 只负责「把 messages + tools 交给模型」
7. `agent/prompt/`、`config.py`、`logger.py`

**数据流（请自己画一遍）：**

用户输入 → `session.add_user` → `llm.chat(session.load(), tools=registry.schemas)` → 若有 `tool_calls` 则 `registry.execute` → `session.add_tool` → 再 `llm.chat` → 直到没有 tool_calls → 打印最终文本。

**已知缺口（读完必须承认，且本版不要修）：**

- `while True` 没有步数上限
- Tool 参数几乎不校验；HTTP 超时靠 requests 默认
- 每次把 Memory 里全部消息送给模型（对话一长会爆上下文、烧钱）
- 只有 CLI，没有多用户 HTTP
- 非流式，用户要等整段结束
- 没有检索、没有用户画像、没有写操作确认、没有评测集

**验收：** D10 的 4 个问题能讲清；能指着文件说清边界。

**给 AI：** 未开始 v0.3 前，不要「顺手」加 max_steps、FastAPI、RAG。

## v0.3 循环加固（4 天 / 12h）

**真实业务里的问题：** 模型可能反复调工具、Tool 抛异常、参数乱写。线上会表现为：请求挂死、账单爆炸、用户看到 500。

**本版只解决什么：** 循环停得住；失败变成「给模型的 Tool 结果」而不是进程崩溃；每轮能看到步数。

**要懂的术语：** Agent 循环、max steps、超时、重试、幂等（入门）、Guardrail（入门）。

**学习任务：**

- Day1：读术语；给 `chat_once` 设计停止条件（最大步数、连续失败次数）
- Day2：Tool 异常捕获，返回 JSON error 字符串，让模型有机会改参数
- Day3：一次对话记录 step count；超限时给用户一句人话，而不是空挂
- Day4：用「故意坏参数 / 故意让天气服务挂掉」做验收

**验收：**

- 模型死循环调工具时，有限步内结束
- 天气服务宕机时，会话可继续，Memory 不被半截状态污染（或能回滚）
- 日志能看出停在第几步、为什么停

**不要做：** 新 Tool、HTTP API、摘要、RAG。

**给 AI：** 只改循环控制与错误回传。Registry 可小改（统一捕获），不要重构目录。

---

## v0.4 Tool 工程化（5 天 / 15h）

**真实业务里的问题：** Tool 就是 Agent 的 API。真实系统里失败最多的是：参数不合法、外部超时、返回太大、不该并行的调用并行了。

**本版只解决什么：** 把 Tool 当后端接口做：校验、超时、返回截断、错误形状统一。最多再加 **1 个** 用于对照模式的 Tool（例如时间或计算器），目的是证明「加 Tool 不用改循环」。

**要懂的术语：** JSON Schema、Pydantic、并行 tool_calls、沙箱（概念）、幂等。

**学习任务：**

- 天气参数校验（空城市、过长字符串）
- 统一 ToolResult：成功 / 校验失败 / 超时 / 上游错误
- 阅读一次响应里多个 `tool_calls` 时，哪些可并发（本版实现或只写清注释+串行也行，但必须理解）
- 第二个 Tool 只为验证 Registry，功能保持极简

**验收：** 新 Tool 不改 `chat_once` 主流程；非法参数不会把 Python 异常打到用户脸上。

**不要做：** 搜索、写库、任意 HTTP 代理（那是沙箱与安全，偏后）。

## v0.5 HTTP 服务 + 多用户 Session（6 天 / 18h）

**真实业务里的问题：** CLI 不是产品。真实形态是：每个用户（或每个窗口）一个 `session_id`，服务端并发处理，历史在 DB。

**本版只解决什么：** FastAPI（或你熟悉的 Web 框架）暴露「创建会话 / 发消息 / 拉历史」。CLI 可保留作调试。

**要懂的术语：** Session ID、多租户（入门）、无状态 HTTP vs 有状态会话、鉴权（本版可先不做，只知道缺口）。

**学习任务：**

- `POST /sessions` 创建，`POST /sessions/{id}/messages` 对话
- 两个 session 交叉提问，历史不得串台
- 进程重启后，PG 中的 session 仍能接着聊（「那上海呢？」）
- 思考：HTTP 超时 vs Agent 可能跑多步 LLM——本版可同步阻塞，但必须在笔记里写明这是问题（v0.6/v1.0 再解）

**验收：** curl 或最小前端可多会话；`session_id` 由客户端持有，不再每次启动 `uuid4()` 丢掉以前的对话。

**不要做：** 流式、登录系统、RAG。

---

## v0.6 流式输出（4 天 / 12h）

**真实业务里的问题：** 用户不能盯着转圈等 10 秒。产品体验取决于首 token 时间，以及 Tool 执行时的中间状态（「正在查天气…」）。

**本版只解决什么：** LLM 文本流式推到客户端（SSE 即可）。Tool 期间推送状态事件。

**要懂的术语：** Streaming、SSE、TTFT、WebSocket（对比即可，不必上）。

**验收：** 最终回答逐字出现；网络断开时服务端行为有定义（取消或跑完丢弃，写在笔记里）。

**不要做：** 上 WebSocket 只为赶时髦；不要同时做摘要。

---

## v0.7 上下文治理（6 天 / 18h）

**真实业务里的问题：** `memory.load()` 全量进模型 = 对话越长越贵、越慢、越容易丢重点，最后触发上下文窗口上限。

**本版只解决什么：** 存储仍可全量（审计）；送给模型的是 **视图**：system + 摘要 + 最近 K 轮。Agent 仍然不知道磁盘细节。

**要懂的术语：** Context Engineering、Token 预算、滑动窗口、摘要 / Compaction。

**学习任务：**

- 区分 `load()`（全量，给 UI/审计）与 `load_for_llm()`（给模型）
- 超阈值时对旧轮次做摘要，摘要也作为 Memory 的一种消息或独立字段
- 估算或记录每次请求 token 数

**验收：** 聊足够多轮后仍能记住关键事实；单次请求 token 明显低于全量 replay；DB 里仍能回放完整历史。

**不要做：** 向量库、用户画像表（下一两版）。

## v0.8 RAG（9 天 / 27h）

**真实业务里的问题：** 模型不会你们公司的文档、政策、商品说明。把知识写进 Prompt 无法维护。真实做法是检索后再回答，并尽量带来源。

**本版只解决什么：** 本地小知识库（Markdown 即可）+ 检索 Tool 或检索后注入；回答能指向来源。天气仍走原 Tool，知识走检索——让模型学会选工具。

**要懂的术语：** RAG、Embedding、Chunking、向量库、Top-k、引用、混合检索（了解即可）。

**学习任务：**

- Day1–2：切片与检索原理，先用最笨的关键词检索跑通闭环
- Day3–5：Embedding + 向量检索（可用现成库，重点在管道不是调参）
- Day6–7：引用与「检索为空时不许编造」
- Day8–9：和天气 Tool 并存时的路由是否合理；写 10 条问答做手工评测

**验收：** 改知识库一句，回答改变且无需改 Prompt；知识库没有的内容会承认不知道，而不是幻觉成天气或政策。

**不要做：** 上多 Agent「研究团队」；不要一上来上云端向量服务（本地够学）。

## v0.9 长期记忆与用户画像（5 天 / 15h）

**真实业务里的问题：** 跨会话仍应记得「我在北京、喜欢简洁回答」。这不能全靠 messages 窗口。真实系统会有用户画像 / 记忆表，按需注入 Prompt。

**本版只解决什么：** 与 Session 消息分离的长期记忆（偏好、稳定事实）。新 Session 能读到，而不是把一辈子对话塞进窗口。

**要懂的术语：** 用户画像、长期记忆、情景记忆 vs 语义记忆、记忆写入策略（何时写、谁写）。

**学习任务：**

- 画像存什么（少而准：城市、语言风格），不存全部聊天
- 谁抽取：规则 / 模型总结 / 用户显式设置——本版选一种，写清权衡
- 新 session 的 system 或前置消息如何注入画像
- 隐私：画像不要打进完整日志

**验收：** 新开 session，无需再说「我在北京」，问「要不要带伞」仍会查北京天气（或先确认城市来自画像）。

**不要做：** 推荐算法、增长运营那套庞大画像；保持小表。

---

## v0.10 Human-in-the-loop（5 天 / 15h）

**真实业务里的问题：** 发邮件、改订单、写数据库不能让模型直接执行。产品形态是：模型提议 → 用户确认 → 再执行 → 模型总结。

**本版只解决什么：** 给一个「写操作」Tool（提醒 / 备忘写入 PG 即可）加确认态。读操作仍自动。

**要懂的术语：** Human-in-the-loop、中断与恢复、破坏性工具、待确认状态。

**验收：** 未确认前 DB 无写入；确认后才执行；拒绝后模型能改口；刷新页面仍能看到待确认项（状态要落库）。

**不要做：** 复杂工作流引擎。一个写 Tool 足够。

---

## v0.11 评测与可观测性（6 天 / 18h）

**真实业务里的问题：** 改 Prompt 或 Tool 描述后，「感觉更好」不是工程。没有黄金集和 Trace，线上只能赌。

**本版只解决什么：**

- 一轮对话一个 `trace_id`：每次 LLM、每次 Tool 的耗时、token、输入输出摘要
- 一份黄金集（15–30 条）：必调天气 / 必不调 / 多轮指代 / 知识库问答 / 确认流
- 可重复跑的评测脚本（先断言「是否调了某 Tool」，再视情况加 LLM-as-judge）

**要懂的术语：** Trace、Span、Eval、黄金集、LLM-as-judge、延迟、成本。

**验收：** 改 `assistant.txt` 一句后能跑评测看回归；能从 Trace 查出某次「不该调工具却调了」。

**不要做：** 上完整商业观测平台（可选用一个开源，但核心是你自己的字段设计）。

## v0.12 路由与技能（5 天 / 15h）

**真实业务里的问题：** 一个入口，后面是不同能力（闲聊 / 查天气 / 查知识库 / 写备忘）。把所有 Tool 每次都塞给模型，会更贵、更容易调错工具。真实做法是路由到不同 Prompt + Tool 子集（技能）。

**本版只解决什么：** 单 Agent 入口 + 路由器（规则或小模型分类均可）+ 2～3 个技能。不是多人格互相开会。

**要懂的术语：** Router、Skill、Multi-agent（对比：何时不需要）、Planner-Executor（了解）、MCP（了解：Tool 的一种标准协议）、Handoff。

**验收：** 闲聊不把天气+检索+写库 schema 全部送进模型；查天气仍稳定；技能之间不串权限（闲聊技能没有写库 Tool）。

**不要做：** 为了「像多智能体」硬拆 5 个互相发消息的 Agent。

---

## v1.0 生产收口（5 天 / 15h）

**真实业务里的问题：** 能演示 ≠ 能值班。缺鉴权、限流、配额、配置、失败分级时，不能叫上线。

**本版只解决什么：** 最小生产集。

- 鉴权（哪怕 API Key）
- 每用户 / 每会话的速率与 token 配额
- 配置与密钥只走环境变量
- 失败分级：模型挂了、工具挂了、DB 挂了，用户看到可读错误，日志有 trace_id
- 启动方式可复制（Docker 或一份清晰的部署说明）
- Prompt injection 最小防护（用户试图覆盖 system、诱骗写操作时的行为有测试）

**要懂的术语：** 限流、配额、Prompt Injection、Guardrail、密钥管理。

**验收：** 能对「同事」只给地址和 Key 就能调；能回答费用从哪看、如何停掉一个失控会话。

**不要做：** Kubernetes 大而全、多区域、企业 SSO——那是岗位环境问题，不是本教程的核心。

---

## 4. 缓冲周怎么用

5 个工作日不要预支给「新功能」。用来：

- 补未通过的验收
- 把各版笔记收成一页「我的架构决策」
- 再走一遍 v0.2 数据流，看自己 3 个月前的理解差在哪

若全部提前完成：用缓冲读一份开源 Agent 运行时源码，对照本文版本（循环、Tool、Memory、HITL、Eval），写差异，而不是引入该框架重写本仓库。

## 5. 进度检查（给自己）

**两周结束：** 术语表 A+B 能用自己的话讲；v0.2 数据流能画。

**第一个月结束（约 v0.6）：** Agent 是一个多用户的流式 HTTP 服务，坏工具打不挂它。

**第二个月结束（约 v0.9）：** 它会检索、会压缩上下文、新会话还认得用户稳定偏好。

**第三个月结束（v1.0）：** 写操作有确认，改 Prompt 有评测，出问题有 Trace，有配额和鉴权。

这时你再去看框架，应能翻译成：「这是他们的 v0.x。」
